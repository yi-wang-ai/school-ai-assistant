# 面试演示脚本（5 分钟）

适用岗位：AI 应用工程师。目标：5 分钟内让面试官看到"能落地、能验证、能解释"。

## 演示前准备（面试前 30 分钟）

```bash
cd ~/Code/dify/docker && docker compose up -d          # 启动 Dify
cd ~/Code/school-ai-assistant && docker compose up -d   # 启动规则服务 + PostgreSQL
curl -s localhost:8000/health                           # 应返回 {"status":"ok"}
```

- 浏览器打开三个标签页：Dify 工作流画布（报销政策助手）、GitHub 仓库 README、一个终端窗口。
- 终端里先 `set -a && . ./.env && set +a`，并定义提问函数：

```bash
ask(){ curl -s -m 200 localhost:8000/ask -H "Authorization: Bearer $1" \
  -H 'Content-Type: application/json' -d "{\"question\":\"$2\"}" \
  | python3 -c "import json,sys;d=json.load(sys.stdin);print(d['answer']);print('引用校验:',d['citation_check']['ok'],'审计编号:',d['audit_id'])"; }
```

- 先各跑一遍下面的问题预热（第一次调用较慢），确认网络和硅基流动接口正常（模型免费，但有调用频率限制）。
- 网络不稳就直接播放备用录屏（见文末）。

## 第 1 分钟：讲清楚问题（不操作，只说）

> 学校财务处每天重复回答报销咨询，政策每年修订，老师常按旧版本准备材料。我做了一个报销政策助手：
> 回答必须有政策出处；金额由程序计算，不让大模型算；普通教职工看不到内部审核细则；每次问答都留审计记录。
> 平台用的是开源的 Dify，我自己写的部分是右边这个规则服务。

指着 README 的架构图，说一句：Dify 负责检索和组织语言，规则服务负责计算、权限和留痕。

## 第 2 分钟：带出处的回答 + 程序计算

```bash
ask "$STAFF_TOKEN" "2026年10月12日到14日去北京出差，住了2晚，每晚600元。住宿、伙食补助和市内交通一共能报多少？"
```

讲解要点：
- 合计 1700 元，超标 100 元个人自理；每一行都有〔FIN-TRAVEL v2 第N条〕。
- 切到 Dify 画布，点"提取出差信息"和"调用规则计算服务"两个节点：数字来自 `calculator.py`，大模型只负责照抄和解释。
- "引用校验: True"：服务检查过每个被引用的条款都真实存在。

## 第 3 分钟：版本切换（政策更新的核心难点）

```bash
ask "$STAFF_TOKEN" "2026年8月30日到9月2日去广州出差，住了8月30日、31日和9月1日三晚，每晚540元。一共能报多少？"
```

讲解要点：
- 出差跨过 2026-09-01 新政策生效日：8 月按 2025 版标准，9 月按 2026 版标准，按天分段，合计 2300 元。
- 程序还发现：出差 9 月 2 日结束，20 日报销期限 9 月 22 日已过，主动提醒逾期。
- 这正是只用 Dify 时失败的题：当时检索只拿到新版政策，模型算不出来。加了规则服务后通过。
- 政策再修订时怎么做：在 `rules.py` 加一个 `PolicyVersion`（生效日期、标准、条款号），上传新文件到知识库，补单元测试，跑一遍评测集。

## 第 4 分钟：权限 + 拒答

```bash
ask "$STAFF_TOKEN"    "差旅报销超过多少钱需要院领导加签？"
ask "$REVIEWER_TOKEN" "差旅报销超过多少钱需要院领导加签？"
ask "$STAFF_TOKEN"    "去日本参加学术会议，住宿标准是多少？"
```

讲解要点：
- 同一个问题，教职工被拒绝，审核人员得到"超过 5000 元"〔FIN-AUDIT v1 第4条〕。
- 角色来自服务器端的用户令牌，不是用户自己选的；最初版本让用户自选角色，任何人都能冒充审核人员，这是我评测时发现并修掉的问题。
- 政策没规定的（出国标准），直接说"未作规定"，建议联系财务处，不编造。

## 第 5 分钟：审计记录 + 评测结果

```bash
docker compose exec -T db psql -U reimburse -c \
  "select id, role, citation_ok, blocked, latency_ms, left(question,20) from audit_log order by id desc limit 5;"
```

切到 GitHub 的评测结果表，讲：
- 39 道测试题，覆盖可回答、版本陷阱、计算、无依据拒答、越权、诱导性问题。
- 付费模型（DeepSeek）：只用 Dify 37/39，加规则服务 39/39。
- 换成免费的 Qwen3-8B 后：小模型会抄错、编造金额、读错日期，所以我把金额明细和行程信息解析都改由代码完成，再加结论写法规则和引用格式校验，最终 38/39（1 题有争议）。
- 为了避免“针对测试题调参”，我在修复前另写了 15 道留出题，修复后 15/15。
- 这是一个成本和质量的取舍：免费模型零成本但更慢（中位 36 秒）、措辞更不稳定。
- 诚实说明局限：题目是我自己出的；关键词自动评分会误判，所以被标记的题都人工复核过；每种配置只跑了一次，小模型每次输出会有差异；响应偏慢，下一步可以减少调用次数。

收尾一句：
> 同一套 Dify 上我还做了课程答疑助手和文献摘要工作流，分别对应教学和科研场景。部署时遇到的 4 个问题和解决办法都记录在 deployment-notes 里。

## 面试官可能追问

| 问题 | 回答要点 |
|---|---|
| 为什么不让大模型直接算钱？ | 大模型算术和日期处理不稳定，金额错了有财务风险；换成免费 8B 模型后这个问题实际出现过（结论 1000 元、自己算 3200 元、正确是 3080 元）。现在金额明细由代码生成，规则可以单元测试（服务端 57 个测试），结果可复现。 |
| 为什么选 Dify？ | 开源、可私有化部署，数据不出校；可视化工作流适合和业务部门一起改流程，也能用于教学；国内院校用得多。 |
| 知识库怎么切分的？ | 政策用父子分块，父块是整份文件，这样每条命中的条款都带着版本号和生效日期；讲义按小节切。讲义最初按行切分导致检索只拿到碎片，改成按标题切后正常。 |
| 怎么防止编造？ | 提示词要求无依据就拒答；服务端校验引用条款是否存在；金额只来自程序；评测集里专门有 6 道无依据题和 6 道诱导题。 |
| 权限怎么做的？ | 用户只拿得到服务的令牌，拿不到 Dify 的 API Key；角色由令牌在服务器端确定；教职工的回答如果引用了内部细则，服务直接拦截。 |
| 数据安全？ | 所有政策是虚构的；部署在本地；模型服务商只收到问题和检索到的条款；如果学校要求数据完全不出校，可以把模型换成本地部署（Ollama）。 |
| 部署遇到什么问题？ | 磁盘超过 90% 导致向量库只读、界面却显示"可用"；服务和 Dify 的容器网络不通；Dify 的 SSRF 代理拦截内网调用，只放行了规则服务一个域名。 |
| 下一步怎么改进？ | 降低延迟（合并调用）；扩大评测集、请财务老师出题；接入统一身份认证代替演示令牌；做成钉钉/企业微信入口。 |
